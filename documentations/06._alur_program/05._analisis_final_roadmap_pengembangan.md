# Analisis Final & Roadmap Pengembangan Sistem IKA UNIMED

## 1. Ringkasan Eksekutif
Berdasarkan evaluasi terhadap dokumen rekomendasi (`04._rekomendasi_langkah_selanjutnya_chatgpt.md`) dan analisis arsitektural sebelumnya (`03._analisis_komprehensif_arsitektur_sistem.md`), saya menyatakan bahwa rencana pengembangan ini **VALID**, **AMAN**, dan **SIAP DIEKSEKUSI**.

Pendekatan **"Membangun Lantai Baru tanpa Meruntuhkan Rumah Lama"** adalah strategi terbaik untuk menjaga stabilitas fitur existing (Berita, Pengaturan Global) sambil membuka kapabilitas baru (Donasi, Karir, Beasiswa).

## 2. Analisis & Validasi Rekomendasi

Berikut adalah hasil bedah teknis terhadap setiap poin rekomendasi:

### A. Arsitektur: Domain-Oriented Modular Monolith
*   **Status:** ✅ **DIADOPSI**
*   **Analisis:** Memisahkan logika bisnis program baru ke dalam folder `app/Domains/` (misal: `Donation`, `Career`) akan mencegah "Spaghetti Code" yang bercampur dengan logika website profil lama.
*   **Implementasi:** Kita akan menggunakan struktur direktori:
    ```
    app/
    ├── Core/           <-- Fondasi Baru (Registry Program, RBAC Program)
    ├── Domains/        <-- Modul Fitur Baru (Donasi, Beasiswa, dll)
    └── Filament/       <-- Admin Panel (Tetap menyatu, tapi resource terpisah)
    ```

### B. Program Registry (`organization_programs`)
*   **Status:** ✅ **DIADOPSI**
*   **Analisis:** Tabel ini mutlak diperlukan sebagai "Saklar Utama" untuk mengontrol visibilitas dan status hidup/matinya sebuah program tanpa perlu deployment ulang.
*   **Struktur Data:** `id`, `name`, `slug`, `status` (active/paused/archived), `visibility`, `icon`.

### C. Hybrid RBAC (Role-Based Access Control)
*   **Status:** ✅ **DIADOPSI dengan Catatan Khusus**
*   **Analisis:** Tantangan terbesar adalah menggabungkan Role Lama (`super_admin`, `editor_pusat`) dengan Role Baru berbasis Program.
*   **Solusi Teknis:**
    *   **Role Lama:** Tetap menggunakan `spatie/laravel-permission` secara global. User dengan role `super_admin` tetap berkuasa penuh.
    *   **Role Baru:** Kita tidak akan mengubah tabel `roles` existing. Kita akan membuat tabel pivot baru `program_user` atau `program_members` yang menyimpan relasi: `user_id` + `program_id` + `role` (misal: 'admin', 'operator').
    *   **Policy Check:** Logika pengecekan akan menjadi:
        ```php
        if ($user->hasRole('super_admin')) return true; // Global Override
        if ($user->isProgramAdmin($programId)) return true; // Program Context
        ```

### D. Skala Prioritas (Phase 1 Foundation)
*   **Status:** ✅ **DIADOPSI**
*   **Analisis:** Memaksa masuk ke fitur Donasi/Payment Gateway tanpa adanya `organization_programs` akan membuat data donasi "menggantung" tanpa induk program yang jelas. Phase 1 (2 minggu) untuk fondasi adalah investasi waktu yang rasional.

## 3. Identifikasi Risiko & Mitigasi

| Potensi Risiko | Mitigasi Teknis |
| :--- | :--- |
| **Kebingungan User Admin** | Pisahkan Menu di Dashboard. Menu "Website Utama" (Berita, Profil) dipisah group-nya dengan Menu "Program Organisasi" (Donasi, Karir). |
| **Konflik Nama Class** | Gunakan Namespace yang ketat. Contoh: `App\Domains\Donation\Models\Transaction` jangan sampai tertukar dengan `App\Models\Transaction` (jika ada). |
| **Beban Database** | Pastikan setiap query ke modul program selalu memfilter `program_id` dan di-index dengan benar. |

## 4. Rencana Aksi Phase 1 (Minggu 1-2)

Kita akan fokus 100% pada **Fondasi Core**, belum menyentuh fitur Donasi/Karir.

### Langkah 1: Strukturisasi Folder
Membuat folder `app/Core` dan `app/Domains` untuk menyiapkan wadah kode yang rapi.

### Langkah 2: Database Migration (Core)
Membuat tabel:
1.  `organization_programs`: Registry program.
2.  `program_members`: Tabel pivot untuk hak akses per program.

### Langkah 3: Model & Trait
Membuat Model `OrganizationProgram` dan Trait `HasProgramRoles` pada User model untuk mempermudah pengecekan hak akses.

### Langkah 4: Filament Resource Management
Membuat menu "Manajemen Program" di dashboard Super Admin untuk mendaftarkan program baru dan menunjuk admin pertamanya.

Tidak ada konflik dengan sistem yang berjalan. Arsitektur yang diusulkan justru memperkuat sistem dengan memberikan batas yang jelas antara "Fitur Website Standar" dan "Aplikasi Program Organisasi".
