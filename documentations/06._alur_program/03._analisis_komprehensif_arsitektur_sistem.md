# Laporan Analisis Komprehensif Arsitektur Sistem IKA UNIMED

## 1. Eksekutif Summary
Berdasarkan analisis mendalam terhadap diskusi perencanaan sistem, arah pengembangan **PackageSection Organisasi** telah berevolusi dari sekadar kumpulan fitur web menjadi **Single Organization Multi-Program Governance Platform**. Sistem ini dirancang untuk menangani multi-program dengan siklus hidup (lifecycle) dinamis, manajemen hak akses yang granular, dan skalabilitas untuk penambahan program baru di masa depan tanpa mengganggu stabilitas sistem utama.

Arsitektur yang disepakati adalah **Domain-Oriented Modular Monolith**, yang menyeimbangkan fleksibilitas modular dengan kesederhanaan operasional (single codebase/database).

## 2. Arsitektur Sistem: Domain-Oriented Modular Monolith

Sistem akan dibagi menjadi dua lapisan utama untuk memastikan keteraturan dan skalabilitas:

### A. Core Layer (`app/Core/`)
Lapisan ini bertindak sebagai fondasi yang tidak boleh bergantung pada modul fitur manapun.
*   **Program Registry**: Menggunakan tabel `organization_programs` sebagai "source of truth" untuk semua program yang aktif, dipause, atau diarsipkan.
*   **Program-Based RBAC**: Sistem otorisasi yang memungkinkan satu user memiliki peran berbeda di program yang berbeda (misal: Admin di Donasi, tapi User biasa di Learning).
*   **Centralized Analytics**: Service agnostik untuk mengumpulkan statistik lintas program demi kebutuhan dashboard pimpinan.

### B. Domain Layer (`app/Domains/`)
Lapisan ini berisi logika bisnis spesifik untuk setiap fitur. Setiap domain harus terisolasi dan hanya berkomunikasi melalui Service Layer.
1.  **Donation**: Manajemen donasi, kampanye, dan integrasi Payment Gateway (Midtrans).
2.  **Scholarship**: Manajemen beasiswa dengan workflow persetujuan bertingkat (State Machine).
3.  **Career**: Job portal untuk alumni dengan fitur matching skill sederhana.
4.  **Learning**: Modul pembelajaran ringan (Lightweight LMS) untuk skill upgrading.

## 3. Analisis Komponen & Spesifikasi Teknis

### 3.1. Core Foundation
*   **Database Schema**: Tabel `organization_programs` akan mengontrol visibilitas (Public/Dashboard) dan status (Active/Paused/Archived).
*   **Security**: Implementasi **Filament Shield** (Spatie Permission) yang dikustomisasi untuk mendukung konteks program (`$user->hasProgramRole($program, 'admin')`).

### 3.2. Modul Prioritas
*   **Donation (Prioritas 1)**:
    *   **Flow**: User -> Donasi -> Snap Token (Midtrans) -> Webhook -> Update Status.
    *   **Kritis**: Validasi signature key Midtrans pada WebhookController wajib diterapkan untuk keamanan.
*   **Career (Prioritas 2 - Engagement)**:
    *   **Struktur**: `job_listings`, `job_applications`, `user_profiles`.
    *   **Fitur**: Pivot table `job_skills` dan `user_skills` untuk pencocokan otomatis.
*   **Scholarship**:
    *   **Workflow**: Menggunakan State Machine (Draft -> Submitted -> Reviewing -> Approved/Rejected).
*   **Learning**:
    *   **Konsep**: "Lightweight Module" (Course -> Modules -> Lessons). Hindari kompleksitas LMS penuh seperti Moodle. Fokus pada delivery konten dan sertifikat sederhana.

### 3.3. Migrasi Data (Legalisir)
*   Fitur Legalisir lama akan dihapus, namun datanya **Wajib Diselamatkan**.
*   **Strategi**: Script migrasi ke tabel `user_documents` + Soft Deletes untuk audit trail.
*   **Storage**: Dokumen dipindah ke `storage/app/private` dengan akses via signed URL/auth route.

## 4. Identifikasi Tantangan & Mitigasi

| Tantangan | Risiko | Strategi Mitigasi |
| :--- | :--- | :--- |
| **Kompleksitas RBAC** | Admin salah memberi akses, kebocoran data antar program. | Unit Testing ketat pada Policy Layer. UI manajemen role yang jelas di Filament. |
| **Konsistensi UI/UX** | Tampilan Dashboard berbeda-beda tiap modul. | Gunakan Filament Resources standar dan komponen Blade/Livewire reusable. |
| **Feature Creep (LMS)** | Modul Learning menjadi terlalu kompleks dan membebani dev. | Batasi fitur MVP hanya pada Video/PDF + Quiz simpel. Tolak fitur kompleks di fase awal. |
| **Payment Webhook** | Status donasi tidak update (missed webhook). | Implementasi mekanisme retry manual dan log webhook yang detail. |

## 5. Rekomendasi Langkah Pengembangan (Roadmap)

Berdasarkan prinsip "Impact First", berikut adalah urutan eksekusi yang disarankan:

### Phase 1: Fondasi Sistem (Minggu 1-2)
*   [ ] Setup struktur folder `Core` dan `Domains`.
*   [ ] Implementasi Migration `organization_programs`.
*   [ ] Implementasi RBAC dengan Filament Shield (Program-Context).
*   [ ] Setup Service Layer dasar.

### Phase 2: Modul Donasi (Minggu 3-4)
*   [ ] Schema Database Donasi.
*   [ ] Integrasi Midtrans (Sandbox & Production).
*   [ ] UI Frontend & Dashboard Donasi.
*   [ ] Testing Webhook.

### Phase 3: Engagement (Karir & Beasiswa) (Minggu 5-8)
*   [ ] Migrasi data User Profile & Dokumen (Legalisir).
*   [ ] Implementasi Modul Karir (Job Portal).
*   [ ] Implementasi Modul Beasiswa dengan State Machine.

### Phase 4: Learning & Analytics (Minggu 9+)
*   [ ] Implementasi Modul Learning Sederhana.
*   [ ] Pembuatan Dashboard Statistik Pimpinan (Centralized Analytics).

## 6. Kesimpulan
Rencana arsitektur ini sudah matang dan siap dieksekusi. Kunci keberhasilannya ada pada **kedisiplinan menjaga isolasi antar modul** dan **tidak terburu-buru membuat fitur kompleks (seperti full LMS)** sebelum fondasi RBAC dan Program Registry kokoh.

**Langkah Selanjutnya yang Disarankan:** Mulai **Phase 1** dengan membuat struktur folder dan migrasi tabel `organization_programs`.
