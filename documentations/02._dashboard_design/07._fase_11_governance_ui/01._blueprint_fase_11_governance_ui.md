## 15. Fase 11: Governance UI untuk Roles & Permissions (Super Admin)

### 15.1. Tujuan Fase 11

- Menyediakan **UI terpusat** bagi `super_admin` untuk:
  - Melihat daftar **roles** Spatie yang ada.
  - Melihat daftar **permissions**.
  - Mengatur assignment:
    - Permission ↔ Role.
    - Role ↔ User.
- Mengurangi ketergantungan pada perubahan manual di seeder ketika organisasi berkembang.
- Menjaga agar:
  - Sumber kebenaran awal tetap berada di **seeder**.
  - UI bertindak sebagai layer governance di atasnya, bukan pengganti total.

---

### 15.2. Kondisi Sebelum Fase 11

- RBAC sudah stabil dan terdokumentasi:
  - Fase 1–8: desain roles & permissions, policy, dan controller.
  - Fase 9: dashboard & sidebar permission-aware.
  - Fase 10: regression test dasar untuk alur `/dashboard`.
- Pengelolaan roles & permissions:
  - Masih berpusat di:
    - Seeder `RolesAndPermissionsSeeder`.
    - Penyesuaian manual via kode / tinker ketika perlu eksperimen.
- Dampak:
  - Perubahan matrix akses membutuhkan developer.
  - Sulit memberikan “kewenangan terbatas” kepada tim internal untuk menyesuaikan akses.

---

### 15.3. Batasan Desain Fase 11

Untuk menjaga sistem tetap terkontrol:

- UI governance:
  - HANYA dapat diakses oleh user dengan peran khusus, misalnya:
    - Role `super_admin`, atau
    - Permission `master.roles.manage`.
- Fase 11 **tidak** akan:
  - Mengizinkan pembuatan role baru sesuka hati tanpa kendali.
  - Mengubah rule bisnis inti yang bergantung pada role/permission tertentu.
- Fase 11 fokus pada:
  - Mengatur assignment role/permission dalam ruang lingkup yang sudah didefinisikan blueprint RBAC sebelumnya.

---

### 15.4. Pendekatan Teknis

Platform pilihan: **Filament Admin**

- Alasan:
  - Sudah menjadi backoffice utama.
  - Terhubung langsung dengan model Spatie Role & Permission.
  - Mendukung policy dan gate bawaan.

Rencana tinggi:

1. Menambah **Resource untuk Role**:
   - Misalnya `RoleResource` yang:
     - Menampilkan daftar role.
     - Menampilkan permissions terkait satu role.
     - Mengizinkan penambahan/penghapusan permissions pada role tertentu (dalam ruang lingkup yang diizinkan).
2. Menambah **Resource untuk Permission** (opsional):
   - Sebagai read-only atau semi-read-only:
     - Menampilkan daftar permission.
     - Memperlihatkan role mana saja yang memiliki permission tersebut.
3. Menambah **UI Assignment Role ke User**:
   - Bisa melalui:
     - Kolom/field tambahan di `UserResource` (jika sudah ada).
     - Atau resource/halaman khusus untuk mengatur role user.

Setiap resource akan dibatasi oleh policy:

- Hanya user dengan permission `master.roles.manage` yang:
  - Boleh mengakses halaman ini.
  - Boleh mengubah assignment role/permission.

---

### 15.5. Integrasi dengan Seeder

Prinsip:

- Seeder tetap menjadi baseline:
  - Mendefinisikan daftar role dan permission “resmi”.
  - Menjaga agar environment baru (mis. staging/production baru) konsisten.
- Fase 11 diharapkan:
  - Tidak merusak idempotensi seeder.
  - Mengizinkan penyesuaian di atas baseline tanpa kehilangan kontrol.

Strategi:

1. Seeder mendefinisikan:
   - Role wajib.
   - Permission wajib.
   - Mapping dasar role-permission.
2. Governance UI:
   - Mengizinkan penyesuaian assignment di production.
   - Perubahan ini akan tercatat di database.
3. Di masa depan, bila diperlukan:
   - Bisa ditambah mekanisme export/import untuk memotret konfigurasi production.

---

### 15.6. Dampak Terhadap Arsitektur

- Layer tambahan:
  - Di atas seeder (baseline),
  - Di bawah policy/controller (enforcer).
- Pengelolaan akses menjadi:
  - Lebih fleksibel bagi super_admin,
  - Tetap aman bagi developer (tidak perlu sering ubah kode).
- Tidak ada perubahan langsung pada:
  - Route publik,
  - Sidebar,
  - Policy yang sudah ada.

---

### 15.7. Langkah Implementasi Fase 11

Tahap implementasi teknis (sudah dieksekusi bertahap):

1. **Analisis model Spatie di project**:
   - Konfirmasi class yang dipakai:
     - Model `Role` (custom atau default).
     - Model `Permission`.
2. **Buat Filament Resource untuk Role** (`App\Filament\Resources\Roles\RoleResource`):
   - List roles:
     - Nama (`name`).
     - Guard (`guard_name`).
     - Jumlah permissions (`permissions_count`).
   - Form:
     - Menampilkan nama dan guard sebagai read-only.
     - Field `permissions` (multiple select, relasi Spatie) untuk mengatur assignment permission ↔ role.
3. **Tambahkan kontrol akses ke RoleResource**:
   - Hanya user dengan permission `master.roles.manage` yang dapat:
     - Melihat daftar role (`canViewAny`).
     - Mengedit role (terbatas).
   - Create & delete role dinonaktifkan di UI untuk menjaga baseline seeder.
4. **Protected Core Roles**:
   - Daftar core roles:
     - `super_admin`, `admin`, `editor`, `writer`, `subscriber`.
   - Untuk core roles:
     - Section form menampilkan warning: perubahan sebaiknya lewat seeder.
     - Field `permissions` di-`disabled` sehingga matrix utama tidak bisa diubah dari UI.
   - Role non-core (misalnya `instructor`, `moderator`) tetap fleksibel diatur via UI.
5. **Integrasi dengan UserResource**:
   - Menambahkan field `roles` (multiple select, relasi Spatie) pada form user:
     - Hanya terlihat jika user saat ini memiliki permission `master.roles.manage`.
   - Menambahkan kolom daftar roles di tabel user (badge) untuk observabilitas.
6. **Uji manual + test otomatis**:
   - Uji manual dengan akun `super_admin`:
     - Hanya `super_admin` yang dapat membuka governance UI.
     - Perubahan assignment role ↔ permission dan role ↔ user tercermin di akses CMS/portal.
   - Menambahkan test feature:
     - Memastikan `admin` tidak dapat mengakses `/admin/roles` (403).
     - Memastikan `super_admin` dapat mengakses `/admin/roles` (200).

---

### 15.8. Hubungan dengan Fase Berikutnya dan Hardening

- Setelah Fase 11 + hardening:
  - Sistem siap untuk:
    - Organisasi besar yang membutuhkan fleksibilitas akses.
    - Pengelolaan hak akses di tangan tim internal (melalui governance UI) dengan batas jelas.
  - Garis batas kewenangan:
    - `super_admin` mengelola struktur matrix akses (melalui permission `master.roles.manage`).
    - `admin` mengelola operasional konten dan data tanpa bisa mengubah matrix role/permission.
- Fase 12:
  - Fokus pada logical unification:
    - Menyatukan decision logic ke Spatie multi-role + permission.
    - Menjadikan kolom `users.role` sebagai legacy field yang hanya dipakai sebagai fallback terkontrol dan metadata.

---

### 15.9. Ringkasan Fase 11

- Menambahkan lapisan **Governance UI** di atas:
  - Seeder roles & permissions,
  - Policy & controller yang sudah ada.
- Memindahkan sebagian beban pengelolaan RBAC:
  - Dari level kode → ke level UI yang dikendalikan super_admin.
- Menjaga agar:
  - Sistem tetap konsisten dengan blueprint Fase 1–10.
  - Perubahan akses tetap melalui jalur yang terdokumentasi dan terkontrol.
