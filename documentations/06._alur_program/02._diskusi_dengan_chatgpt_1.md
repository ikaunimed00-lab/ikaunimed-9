# 🔷 1️⃣ Macro Decision: Modular Monolith – YA, tapi Jangan Over-Engineering

Rekomendasi trae.ai tentang *Modular Monolith* itu **benar**, tapi perlu disederhanakan.

Untuk skala organisasi alumni (bukan startup unicorn), arsitektur terbaik adalah:

> **Domain-Oriented Modular Monolith (tanpa plugin engine kompleks)**

Artinya:

* Modular di level folder & service
* Tapi tetap 1 codebase, 1 database
* Tidak perlu plugin engine dinamis terlalu dini

⚠ Jangan langsung bikin sistem plugin enable/disable kompleks kalau belum ada kebutuhan nyata.

# 🔷 1️⃣ Pisahkan Konsep: “Presentation Layer” vs “Domain Layer”

Masalah terbesar yang sering terjadi:

Orang membangun fitur berdasarkan halaman, bukan berdasarkan domain.

Padahal yang benar:

```
Domain (Logic & Data)
      ↓
Application Layer (Service)
      ↓
Presentation (Landing + Dashboard)
```

Artinya:

Landing dan Dashboard tidak boleh punya logic sendiri-sendiri.
Mereka hanya “menampilkan pintu masuk” ke domain yang sama.

# 🧠 2️⃣ Program-Based RBAC (INI KRUSIAL)

Karena tiap program bisa punya admin berbeda.

Jangan hanya pakai role global seperti:

* admin
* super_admin

Itu tidak cukup.

Anda perlu:

```
program_user_roles
- id
- user_id
- program_id
- role (admin, reviewer, operator, manager)
```

Dengan ini:

* User bisa admin di Program A
* Tapi hanya viewer di Program B

Ini jauh lebih fleksibel daripada role global.

Gunakan policy berbasis:

```
$user->hasProgramRole($program, 'admin')
```

# 🔄 3️⃣ Program Lifecycle

Karena program bisa dihentikan sementara.

Gunakan status enum:

* active
* paused
* archived

Behavior:

### active

* Tampil di landing
* Tampil di dashboard
* Bisa diakses penuh

### paused

* Tampil (opsional)
* Tidak bisa transaksi / submit form
* CTA disabled

### archived

* Tidak tampil public
* Data tetap ada
* Statistik tetap masuk laporan pimpinan

Jangan pernah hard delete program.
