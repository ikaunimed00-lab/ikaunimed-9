## 16. Fase 12: Logical Unification RBAC (Spatie + Legacy users.role)

### 16.1. Tujuan Fase 12

- Menyatukan seluruh **decision logic otorisasi** ke satu sumber kebenaran:
  - Spatie multi-role + permission.
- Menurunkan peran kolom `users.role`:
  - Dari primary authority → menjadi legacy + fallback transisi.
- Menjaga transisi yang aman:
  - Tidak memutus akses user lama secara tiba-tiba.
  - Menjaga sistem tetap stabil selama migrasi.

---

### 16.2. Konsep Utama: hasSystemRole() dan systemRoleLabel()

Di `App\Models\User` diperkenalkan dua abstraction layer:

- `hasSystemRole(array|string $roles): bool`
  - Prioritas:
    1. Jika user sudah punya Spatie role:
       - Menggunakan `hasRole($roles)` dari Spatie.
    2. Jika belum:
       - Membaca kolom legacy `users.role` (fallback).
  - Tujuan:
    - Semua cek role di kode (admin/editor/writer/subscriber) lewat pintu yang sama.
    - Memungkinkan kita mematikan fallback nanti tanpa memodifikasi seluruh call-site.

- `systemRoleLabel(): ?string`
  - Mengembalikan label role utama untuk UI:
    - Jika user punya Spatie role:
      - Prioritas: `super_admin` → `admin` → `editor` → `writer` → `subscriber`.
    - Jika tidak:
      - Mengembalikan isi kolom legacy `users.role`.
  - Tujuan:
    - Menyediakan **label tunggal** untuk frontend (Inertia) tanpa perlu tahu detail implementasi.

---

### 16.3. Perubahan pada Decision Logic

Semua keputusan akses penting dipindahkan ke abstraction layer ini:

- Redirect setelah login (`App\Listeners\RedirectAfterLogin`):
  - Sebelumnya:
    - Menggunakan `in_array($user->role, [...])`.
  - Sekarang:
    - Menggunakan `$user->hasSystemRole(['admin', 'editor', 'writer'])`.

- Penentu route dashboard utama (`DashboardController::getDashboardRoute()`):
  - Sebelumnya:
    - Berdasarkan `users.role` langsung.
  - Sekarang:
    - Menggunakan:
      - `$user->hasSystemRole(['admin', 'editor', 'writer'])` untuk `/admin`.
      - `$user->hasSystemRole('subscriber')` untuk dashboard subscriber.

- Middleware role (`RoleMiddleware`, `EnsureUserRole`):
  - Sebelumnya:
    - Mengecek `in_array($request->user()->role, $roles)`.
  - Sekarang:
    - Menggunakan `$request->user()->hasSystemRole($roles)`.

- Segmentasi view News dashboard (`NewsController`):
  - Sebelumnya:
    - `match ($user->role)` untuk menentukan view admin/editor/writer.
  - Sekarang:
    - Menggunakan `hasSystemRole()` untuk memilih view yang sesuai.

- Akses panel Filament (`User::canAccessPanel()`):
  - Menambahkan prioritas khusus:
    - Jika user memiliki Spatie role `super_admin` → selalu bisa akses panel.
    - Selain itu mengikuti `isWriter()` (admin, editor, writer).

Implikasi:

- Tidak ada lagi **decision logic baru** yang membaca `users.role` mentah.
- Semua alur kritis sekarang tergantung pada:
  - Spatie roles, atau
  - Abstraksi `hasSystemRole()` yang terkontrol.

---

### 16.4. Perubahan pada Layer UI / Props Inertia

- Shared props Inertia (`HandleInertiaRequests`):
  - Sebelumnya:
    - `auth.user.role` diisi dari kolom `users.role`.
  - Sekarang:
    - `auth.user.role` diisi dari `$request->user()->systemRoleLabel()`.
  - Tambahan:
    - `auth.user.roles` dan `auth.user.permissions` tetap berasal dari Spatie.

- Dashboard Job Vacancy & Course:
  - Props `userRole` yang dikirim ke Inertia sekarang memakai `systemRoleLabel()`:
    - Job Vacancy Dashboard (index).
    - Course Dashboard (index & participants).

Implikasi:

- Frontend tetap menerima `role` dalam bentuk string sederhana.
- Sumber nilai tersebut sekarang:
  - Spatie role jika ada (single source of truth),
  - Legacy kolom `role` hanya jika user belum termigrasi.

---

### 16.5. Sinkronisasi Mutasi User dengan Spatie Roles

Untuk menghindari dual-state saat mengubah data user:

- Registrasi user baru (Fortify: `CreateNewUser`):
  - Mengisi kolom `role` dengan `subscriber`.
  - Sekaligus memanggil `$user->assignRole('subscriber')`.

- Registrasi via Google OAuth (`OAuthController`):
  - Membuat user baru dengan legacy `role = alumni`.
  - Sekaligus memanggil `$user->assignRole('subscriber')`:
    - Hak akses portal mengikuti role `subscriber`.
    - Label `alumni` di kolom legacy bisa dipertahankan sebagai metadata, bukan penentu akses.

- Admin mengubah role user (`Admin\UserController@update`):
  - Meng-update kolom `role` sesuai input.
  - Sekaligus memanggil `$user->syncRoles([$validated['role']])`.

Implikasi:

- Setiap user baru **selalu** lahir dengan Spatie role yang sesuai.
- Perubahan role di admin panel selalu disinkronkan ke Spatie.
- Fallback ke kolom `users.role` hanya benar-benar diperlukan untuk user lama yang belum pernah disentuh alur baru.

---

### 16.6. Audit User Tanpa Spatie Role

Untuk mempersiapkan fase akhir (Spatie-only), ditambahkan perintah artisan:

- `App\Console\Commands\AuditSpatieRoles`
  - Signature:
    - `rbac:audit-users-without-roles {--limit=50}`
  - Fungsi:
    - Menghitung jumlah user yang tidak memiliki Spatie role sama sekali (`doesntHave('roles')`).
    - Menampilkan sampai `limit` user pertama dengan kolom:
      - `id`, `email`, dan legacy `role`.

Contoh penggunaan:

```bash
php artisan rbac:audit-users-without-roles
php artisan rbac:audit-users-without-roles --limit=100
```

Tujuan:

- Memberikan visibilitas penuh atas user lama yang belum termigrasi.
- Menjadi dasar untuk:
  - Menyiapkan script/command migrasi Spatie role untuk user tersebut.
  - Menentukan kapan aman untuk mematikan fallback di `hasSystemRole()`.

---

### 16.7. Status Kolom `users.role` Setelah Fase 12 (Logical)

Setelah langkah-langkah di atas:

- Kolom `users.role`:
  - Tidak lagi digunakan langsung dalam decision logic otorisasi.
  - Berfungsi sebagai:
    - Fallback terkontrol di `hasSystemRole()` dan `systemRoleLabel()`.
    - Metadata legacy dan alat bantu analisis (misalnya filter di `Admin\DatabaseController`).
- Sumber utama kebenaran hak akses:
  - Spatie multi-role + permission.

Rencana jangka berikutnya:

- Setelah:
  - Semua user aktif memiliki Spatie role yang sesuai.
  - Seeder dan modul operasional tidak lagi bergantung pada `users.role`.
  - Audit menunjukkan tidak ada (atau sangat sedikit) user tanpa role.
- Maka:
  - `hasSystemRole()` dapat diubah menjadi Spatie-only.
  - Kolom `users.role` bisa ditandai deprecated dan pada akhirnya dijadwalkan untuk di-drop melalui migration terpisah.

---

### 16.8. Ringkasan Fase 12

- Logical unification:
  - Decision logic otorisasi, middleware, dan routing kini bertumpu pada Spatie + abstraction layer.
- Fallback legacy:
  - Tetap ada, tetapi terlokalisasi di satu tempat dan diperlakukan sebagai fase transisi.
- Guard tambahan:
  - User baru (Fortify + OAuth) selalu mendapatkan Spatie role.
  - Update role via admin selalu meng-sync Spatie role.
- Observabilitas:
  - Disediakan perintah artisan untuk mengaudit user tanpa Spatie role.

Fase 12 menyiapkan sistem agar di masa depan dapat beralih ke mode **Spatie-only** dengan risiko minimal, tanpa kehilangan kendali selama masa transisi.
