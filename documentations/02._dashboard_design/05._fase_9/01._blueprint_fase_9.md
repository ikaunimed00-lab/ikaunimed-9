## 13. Fase 9: Dashboard & Sidebar Berbasis Role + Permission

Pada Fase 9, fokus bergeser ke **UX dashboard** (sidebar Inertia) agar:

- Menjadi konsisten dengan sistem **Spatie roles & permissions** yang sudah kita bangun di Fase 1–8.
- Mengurangi ketergantungan pada `users.role` mentah, tanpa merusak pengalaman pengguna yang sudah nyaman.

### 13.1. Tujuan Fase 9

- Menjadikan **dashboard sidebar** (Admin/Editor/Writer/Subscriber) sebagai:
  - Cerminan akurat dari **role + permission** user,
  - Bukan sekadar hard-coded daftar berdasarkan string role.
- Menjaga:
  - **Backward compatibility** (perubahan bertahap, tidak mematahkan flow sekarang),
  - **Single source of truth** di frontend untuk konfigurasi menu (tetap di satu file config).

Hasil yang diharapkan:

- Admin/Editor/Writer/Subscriber melihat **menu yang benar-benar relevan** dengan hak akses mereka.
- Perubahan hak akses (di seeder Spatie) otomatis tercermin di sidebar tanpa perlu mengubah layout satu per satu.

### 13.2. Kondisi Saat Ini

**Frontend:**

- Single source of truth dashboard menu:  
  - File: `resources/js/config/sidebar-menu-config.ts`
  - Tipe:
    - `UserRole = "admin" | "editor" | "writer" | "subscriber"`
    - `MenuItem { title, route, icon, roles: UserRole[] }`
  - Logika:
    - `getMenuByRole(role)` → filter `SIDEBAR_MENU` berdasarkan array `roles`.

- Layout Inertia:
  - `AdminLayout.tsx`:
    - Mengambil menu dengan `getMenuByRole("admin")`.
  - `EditorLayout.tsx`:
    - Mengambil menu dengan `getMenuByRole("editor")`.
  - `WriterLayout.tsx`:
    - Mengambil menu dengan `getMenuByRole("writer")`.
  - `SubscriberLayout.tsx`:
    - Mengambil menu dengan `getMenuByRole("subscriber")` (atau varian lain).

- Redirect ke dashboard:
  - `HandleInertiaRequests::dashboardRoute()`:
    - Menggunakan `match ($user->role)`:
      - `'admin', 'editor', 'writer' => '/admin'`
      - selain itu → `dashboard.subscriber`.

**Backend:**

- Spatie Permission sudah lengkap (Fase 1–7):
  - Roles: `super_admin`, `admin`, `editor`, `writer`, `instructor`, `moderator`, `subscriber`.
  - Permissions: `cms.*`, `site.*`, `elearning.*`, `portal.*`, `alumni.*`, dll.
- Otorisasi:
  - Filament, controller CMS, dan policy portal sudah menggunakan `can('...')` / `hasRole(...)`.

**Gap utama:**

- Sidebar dashboard frontend **belum** berbasis permission:
  - Menu masih berdasarkan `roles: UserRole[]` statis.
  - Belum ada korelasi eksplisit ke permission Spatie.
- Routing dashboard (`/dashboard`, `/admin`) masih mengacu ke `users.role` lama.

### 13.3. Prinsip Desain Fase 9

1. **Tidak memindahkan single source of truth menu dari frontend**  
   - `SIDEBAR_MENU` tetap menjadi master config menu dashboard.
   - Backend tidak akan meng-generate daftar menu satu per satu.

2. **Tambah lapisan “permission-awareness”** di sekitar config yang sudah ada:
   - Kita tidak menghapus `roles: UserRole[]`,
   - Tetapi menambahkan metadata baru: `requiredPermissions` / `requiredAnyPermissions`.

3. **Backend tetap jadi penentu keamanan final**:
   - Walaupun menu muncul di sidebar, akses endpoint tetap dijaga:
     - Policy,
     - Middleware,
     - Permission check.
   - Fase 9 hanya menyelaraskan **visibility** menu dengan access control yang sudah ada.

4. **Transisi bertahap**:
   - Langkah awal:
     - Tambahkan metadata permission di config, tapi belum dipakai.
   - Langkah lanjutan:
     - Layout mulai menyaring menu berdasarkan permission yang dikirim dari backend (via props Inertia).

### 13.4. Desain Struktur Data Menu Baru

Di `sidebar-menu-config.ts`:

- Perluasan interface `MenuItem`:

  - Tambahan properti:
    - `requiredPermissions?: string[]`  
      Daftar permission yang **harus semua dimiliki** user untuk menampilkan menu.
    - `anyPermissions?: string[]`  
      Daftar permission yang cukup **salah satunya dimiliki** user.

- Contoh:

  ```ts
  export interface MenuItem {
      title: string;
      route: string;
      icon: any;
      roles: UserRole[];
      requiredPermissions?: string[];
      anyPermissions?: string[];
  }
  ```

- Contoh mapping:

  - Kelola Berita (CMS News):

    ```ts
    {
        title: "Kelola Berita",
        route: "filament.admin.resources.news.index",
        icon: Newspaper,
        roles: ["admin", "editor", "writer"],
        anyPermissions: ["cms.news.view", "cms.news.create", "cms.news.edit", "cms.news.publish"],
    }
    ```

  - Site Settings (hanya admin):

    ```ts
    {
        title: "Site Settings",
        route: "filament.admin.resources.site-settings.index",
        icon: Database,
        roles: ["admin"],
        anyPermissions: ["site.settings.view", "site.settings.edit"],
    }
    ```

  - Kursus Saya (dashboard instruktur/writer/admin):

    ```ts
    {
        title: "Kursus Saya",
        route: "dashboard.courses.index",
        icon: GraduationCap,
        roles: ["admin", "editor", "writer"],
        anyPermissions: ["elearning.course.view"],
    }
    ```

### 13.5. Data Permission ke Frontend

Agar frontend bisa menyaring menu berdasar permission:

- Di middleware Inertia (`HandleInertiaRequests`):
  - Tambahkan shared prop:
    - `auth.user.permissions` → array string permission milik user saat ini.
    - `auth.user.roles` → array roles Spatie (sebagai referensi tambahan).

- Dengan demikian:
  - Layout Inertia bisa memanggil helper seperti:
    - `filterMenuByPermissions(menuItems, auth.user.permissions)`.

### 13.6. Helper Filtering Menu

Tambahkan helper di frontend (bisa di file yang sama dengan config atau file util terpisah):

- Fungsi:

  ```ts
  export function filterMenuForUser(
      items: MenuItem[],
      userPermissions: string[]
  ): MenuItem[] {
      return items.filter((item) => {
          // Filter dasar: sudah cocok role (getMenuByRole)
          // Tambahan: cek permission jika ada
          if (item.requiredPermissions?.length) {
              const hasAll = item.requiredPermissions.every((p) =>
                  userPermissions.includes(p)
              );
              if (!hasAll) return false;
          }

          if (item.anyPermissions?.length) {
              const hasAny = item.anyPermissions.some((p) =>
                  userPermissions.includes(p)
              );
              if (!hasAny) return false;
          }

          return true;
      });
  }
  ```

- Alur pemanggilan di layout:

  1. Ambil base menu berdasarkan role:
     - `const baseMenu = getMenuByRole('admin');`
  2. Saring berdasarkan permission:
     - `const menuItems = filterMenuForUser(baseMenu, auth.user.permissions);`

### 13.8. Sinkronisasi dengan Redirect Dashboard

Backend yang perlu diselaraskan:

- `HandleInertiaRequests::dashboardRoute(Request $request)`
- `DashboardController::getDashboardRoute(User $user)` (jika masih dipakai)
- `FortifyServiceProvider` redirect setelah login (sudah sebagian menggunakan `hasAnyRole`)

Blueprint Fase 9:

- Standarisasi logika “siapa ke /admin, siapa ke dashboard subscriber”:

  - Gunakan Spatie roles terlebih dahulu:
    - Jika user `hasAnyRole(['admin', 'editor', 'writer'])` → `/admin`.
    - Jika `hasRole('subscriber')` → `route('dashboard.subscriber')`.
  - Kolom `users.role` tetap bisa dipakai sebagai fallback selama masa transisi.

- Catat bahwa:
  - Menu di frontend sudah permission-aware,
  - Redirect di backend mengikuti role Spatie,
  - Akses aktual ke resource tetap dijaga oleh policy & permission.
