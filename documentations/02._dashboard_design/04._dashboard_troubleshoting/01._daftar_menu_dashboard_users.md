**1. Mengapa Writer bisa melihat “Programs”, “Homepage Sections”, dan “Site Settings”?**

Menu‑menu yang Anda sebut itu bukan datang dari sidebar React (Inertia), tapi dari **panel Filament** (`/admin`). Aksesnya diatur oleh:

- `User::canAccessPanel(Panel $panel)` di [User.php](file:///d:/Documents/WEBSITE/ikaunimed-9.or.id/app/Models/User.php):

  ```php
  public function canAccessPanel(Panel $panel): bool
  {
      return $this->isWriter(); // admin, editor, and writer can access
  }

  public function isWriter(): bool
  {
      return in_array($this->role, ['admin', 'editor', 'writer']);
  }
  ```

  Artinya:
  - Semua user dengan role `admin`, `editor`, `writer` dianggap “panel user”.
  - Mereka semua boleh masuk ke Filament (`/admin`).

- Di dalam Filament, **tiap Resource** bisa menambah pembatasan tambahan dengan `canViewAny()`. Kalau tidak ada `canViewAny()`, maka **semua panel user (admin/editor/writer)** boleh melihat resource tersebut di menu.

Sekarang lihat resource yang Anda tanyakan:

- **Programs**  
  [OrganizationProgramResource.php](file:///d:/Documents/WEBSITE/ikaunimed-9.or.id/app/Filament/Resources/OrganizationProgramResource.php)

  ```php
  class OrganizationProgramResource extends Resource
  {
      protected static ?string $model = OrganizationProgram::class;

      protected static string|BackedEnum|null $navigationIcon = 'heroicon-o-squares-2x2';
      protected static ?string $navigationLabel = 'Programs';
      protected static ?int $navigationSort = 1;

      // TIDAK ada canViewAny()
  }
  ```

  Karena tidak ada `canViewAny()`, maka:
  - Semua **panel user** (admin, editor, writer) melihat menu “Programs”.

- **Homepage Sections**  
  [HomepageSectionResource.php](file:///d:/Documents/WEBSITE/ikaunimed-9.or.id/app/Filament/Resources/HomepageSections/HomepageSectionResource.php)

  ```php
  class HomepageSectionResource extends Resource
  {
      protected static ?string $model = HomepageSection::class;

      protected static string|BackedEnum|null $navigationIcon = Heroicon::OutlinedHome;
      protected static \UnitEnum|string|null $navigationGroup = 'Site Management';

      // TIDAK ada canViewAny()
  }
  ```

- **Site Settings**  
  [SiteSettingResource.php](file:///d:/Documents/WEBSITE/ikaunimed-9.or.id/app/Filament/Resources/SiteSettings/SiteSettingResource.php)

  ```php
  class SiteSettingResource extends Resource
  {
  ```

Keduanya juga **tidak punya `canViewAny()`**, sehingga:

- Writer = panel user → ikut mendapat menu:
  - “Homepage Sections (Site Management)”
  - “Site Settings (Site Management)”

Jadi jawaban singkat poin (1):

> Writer bisa melihat Programs, Homepage Sections, dan Site Settings karena resource‑resource itu **tidak dibatasi** secara khusus, sehingga secara default **semua role panel (admin/editor/writer) boleh mengaksesnya**.

Secara teknis benar, tapi dari sisi desain peran, ini artinya writer punya wewenang cukup besar di area **Site Management**, yang biasanya hanya dipegang oleh admin.

**3. Apakah daftar menu pada Admin & Writer sekarang sudah “benar”?**

Kalau kita mapping dengan role:

- **Writer (daftar yang Anda lihat):**
  1. Job Vacancies
  2. Scholarships
  3. Programs
  4. Homepage Sections (Site Management)
  5. Site Settings (Site Management)
  6. News

  Di balik layar:

  - `JobVacancyResource`: tidak dibatasi → semua panel user (admin/editor/writer).
  - `ScholarshipResource::canViewAny()` mengembalikan `auth()->user()?->isWriter()` → admin/editor/writer.
  - `NewsResource`: juga panel user (admin/editor/writer).
  - `OrganizationProgramResource` (Programs): tidak dibatasi → panel user (admin/editor/writer).
  - `HomepageSectionResource` & `SiteSettingResource`: tidak dibatasi → panel user (admin/editor/writer).

  Secara **fungsi teknis**, tidak ada yang “salah”; sistem berjalan sesuai aturan yang ada.

  Tapi secara **desain peran**, pola yang terbentuk adalah:

  - Writer bisa:
    - Mengelola konten (News, Job Vacancies, Scholarships) → ini wajar.
    - Mengelola struktur program organisasi (Programs) → tergantung konsep; bisa wajar kalau writer Anda dianggap content admin untuk program.
    - Mengelola tampilan beranda dan konfigurasi situs (Homepage Sections, Site Settings) → ini biasanya level **admin**, bukan writer.

- **Admin (daftar yang Anda lihat):**
  1. Job Vacancies
  2. Legalizations
  3. Scholarships
  4. Programs
  5. Alumni Post (Moderasi)
  6. Homepage Sections (Site Management)
  7. Site Settings (Site Management)
  8. News (Konten)
  9. Organizations (Master Data)
  10. Users (Master Data)

  Ini sangat konsisten dengan peran admin:

  - Bisa mengelola semua konten dan master data.
  - Bisa mengelola site management (Homepage, Settings).
  - Bisa moderasi (Alumni Post).
  - Bisa mengelola organisasi dan user.

**Evaluasi:**

- **Secara teknis:**  
  - Role Admin: sudah sesuai (superuser).
  - Role Writer: secara teknis boleh, tapi haknya **lebih besar** dari writer biasa (karena bisa mengubah homepage & settings).

- **Secara konsep peran (best practice umum):**
  - Writer biasanya:
    - Fokus di **konten** (News, Job Vacancies, Scholarships).
    - Tidak menyentuh:
      - konfigurasi situs,
      - layout homepage,
      - master program organisasi (kecuali mereka memang product owner).
  - Admin:
    - Boleh semua, termasuk Site Management dan master data.

Jadi jawaban jujur untuk poin (3):

> - Dari sisi kode, daftar menu Admin & Writer **konsisten dengan aturan yang sekarang ada** (semua panel user = admin/editor/writer, kecuali resource yang dibatasi khusus).
> - Dari sisi desain peran, **Writer saat ini punya akses terlalu luas** (Programs + Site Management) jika yang Anda bayangkan adalah writer konten biasa. Kalau yang Anda mau:  
>   - Writer hanya pegang konten (News, Job Vacancies, Scholarships),  
>   - sementara **Programs, Homepage Sections, dan Site Settings** hanya untuk Admin (dan mungkin Editor),  
>   maka resource‑resource tersebut perlu diberi `canViewAny()` yang membatasi ke role yang sesuai.

Jika Anda sudah mantap memutuskan pola peran yang diinginkan (misalnya: “Programs + Site Management hanya boleh Admin, Editor boleh sebagian, Writer hanya konten”), saya bisa lanjutkan dengan:

- merapikan `canViewAny()` di:
  - `OrganizationProgramResource`
  - `HomepageSectionResource`
  - `SiteSettingResource`
- dan bila perlu menjelaskan di dokumentasi “Role & Menu” agar ke depan tidak perlu meraba lagi siapa boleh mengakses apa.

# 🟢 FASE 1 — Tambah Multi-Role Tanpa Hapus role Lama

### Langkah:

1. Buat tabel `roles`
2. Buat tabel `user_roles`
3. Seed role default
4. Migrasikan data lama:

Mapping:

| users.role lama | roles baru |
| --------------- | ---------- |
| admin           | admin      |
| editor          | editor     |
| writer          | writer     |
| subscriber      | subscriber |

Semua user lama tetap punya 1 role.

Sistem lama masih jalan karena:

* `users.role` masih ada
* method `isWriter()` dll masih pakai kolom lama

Tidak ada yang rusak.

---

# 🟡 FASE 2 — Tambah Helper Baru Tanpa Hapus Lama

Tambahkan method baru di User:

Contoh konsep:

```php
public function roles()
{
    return $this->belongsToMany(Role::class);
}

public function hasRole($role)
{
    return $this->roles()->where('name', $role)->exists();
}
```

Lalu ubah pelan-pelan:

Dari:

```php
$this->role === 'admin'
```

Menjadi:

```php
$this->hasRole('admin')
```

Tapi JANGAN hapus method lama dulu.
